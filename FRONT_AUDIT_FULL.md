## 4) Networking e Services (100% detalhado)
### 4.1 HTTP Client (`services/api.ts`)
- Base URL: `API_BASE_URL` obtido de `Constants.expoConfig.extra.backendApiUrl`, `globalThis.env`, `process.env.API_BASE_URL` e, na falta, `http://localhost:3000`; a build dispara alerta em runtime se a URL conter `localhost` fora de dev (`services/api.ts:17-45`).
- Request interceptors: adicionam `Authorization: Bearer ${token}` do AsyncStorage (`services/api.ts:76-83`), geram `Idempotency-Key` para POST/PUT/PATCH em caminhos sensíveis definidos em `IDEMP_PATHS` (`services/api.ts:49-62`, `services/api.ts:84-95`), e injeta `X-Client-Request-Id` (`services/api.ts:93-95`).
- Response interceptors: `buildUnifiedError` uniformiza status/mensagens/requestId (`services/api.ts:106-117`), permite fallback de guest em `/users/me` (`services/api.ts:126-158`), aplica retry exponencial para 5xx (`services/api.ts:163-166`), respeita `x-silent` e `meta.silent` para suprimir toasts (`services/api.ts:168-186`), envia exceções ao Sentry com `tags.scope = 'network'` (`services/api.ts:188-194`), e executa `onUnauthorizedCallback` (AuthContext) antes de apagar AsyncStorage e mostrar toast genérico `common.unauthorized_error` (`services/api.ts:196-225`).
### 4.2 Cada service (services/*.ts)
- **`services/authService.ts`**: login/logout e persistência AsyncStorage (`services/authService.ts:29-228`), `refreshSession` chama `/auth/refresh` (`services/authService.ts:59-76`) mas não está conectado automaticamente ao interceptor; `storeAuthData`/`saveAuthData` gravam `auth_token`, `user_role`, `user_id`, `user_profile` e atualizam `api.defaults.headers.Authorization` (`services/authService.ts:189-228`).
- **`services/bookingService.ts`**: `createBooking` POST `/bookings` com DTO tipado (`services/bookingService.ts:16-29`), `getBookingsForUser` GET `/bookings/me` com conversão de status e filtros (`services/bookingService.ts:31-54`), demais mutações (start/complete/cancel/accept, chat checks) tratam erros 4xx/5xx com mensagens genéricas e fallback silencioso (`services/bookingService.ts:56-217`).
- **`services/paymentService.ts`**: `createPixCharge` POST `/payments/pix-charge` com `idempotency-key` determinístico `pix-{bookingId}-{providerId}-{amount}` e normaliza status CANCELLED -> EXPIRED (`services/paymentService.ts:10-33`); `fetchPaymentIntent` GET `/payments/intent/:bookingId` com `x-silent` flag, trata 404 como `null` e 401 criando erro com `status=401` (`services/paymentService.ts:53-75`).
- **`services/providerService.ts`**: `getProviderDetails` (`services/providerService.ts:190-225`) incorpora `ReviewService`, `getProviderAvailability` (`services/providerService.ts:229-249`), `getMyProviderAvailability`/`updateMyProviderAvailability` para provedores logados (`services/providerService.ts:256-314`), além de busca silenciosa de provedores (`services/providerService.ts:541-598`).
- **`services/configService.ts`**: `getPricingConfig` consulta `/config/pricing`, mantém cache e recorre ao fallback `minHourlyMinutes = 240` em falhas (`services/configService.ts:1-33`).

## 9) Lista de GAPS
1. **Mínimos de hora hardcoded antes do pricing config** (`app/client/bookings/schedule-service.tsx:54-575`, `app/provider/schedule/manage-availability.tsx:177-611`, `hooks/useProviderAvailability.ts:21-203`). Impacto: se `/config/pricing` muda o backend (`MIN_HOURLY_MINUTES` central no backend), os slots exibidos/permitidos ficam fora de sincronia. Recomendo bloquear a UI até `getPricingConfig()` resolver e eliminar as constantes locais.
2. **Auth expira sem refresh automático** (`services/api.ts:196-215`, `contexts/AuthContext.tsx:122-149`, `services/authService.ts:59-76`). Há um `refreshSession` mas o interceptor apenas desloga; sessions longas (Ads/QA) são forçadas a login. Recomendo tentar `authService.refreshSession()` antes de limpar AsyncStorage e só abandonar se o refresh falhar.
3. **Toast/Sentry não expõem requestId/bookingId** (`services/api.ts:106-117`, `services/api.ts:183-195`). Ainda que `buildUnifiedError` extraia `requestId`, o toast só mostra o texto traduzido e o Sentry não recebe `requestId` como tag, dificultando rastreamento dos `X-Client-Request-Id` gerados. Recomendo anexar `unified.requestId`/`bookingId` aos toasts e tags Sentry.
4. **Floating pill ignora `PENDING_PROVIDER_CONFIRMATION`** (`app/_layout.tsx:88-114`, `types/backend/bookings.ts:13-23`). Se o backend criar essa “etapa pendente”, o pill desaparece porque só considera `IN_PROGRESS`/`CONFIRMED`. Atualize o filtro para novos status notificados pelo backend.
